# Unison Agent Instructions

## Formatting

- Wrap comments at a 120-character column limit, not a shorter width.
- Indent continuation lines inside a comment with spaces placed after the comment marker. The marker itself keeps
  whatever tab indentation the formatter gives it.
- Format Go code with `golangci-lint fmt`, which runs gofumpt with this repo's extra rules, never with `gofmt`.
  `./build.sh -f` checks the formatting without changing anything.

## Comments

Any comments you add or edit:

- Should be checked for correctness.
- Should be as concise as possible.
- Exported identifiers always get a doc comment; otherwise omit comments when the code is obvious.

## Source conventions

- Every `.go` file carries the MPL 2.0 copyright header found at the top of any existing source file (generated files
  put their "Code generated" line ahead of it). The `goheader` linter rejects a file that lacks it, so copy the header
  into every new file.
- The module is cgo-free and must stay that way: `./build.sh` stops if any file imports `"C"`.
- The `*_gen.go` files under `enums` are generated by `cmd/enumgen` from the `enumInfo` definitions in its `main.go`
  and from `enum.go.tmpl`. Every regeneration deletes each `*_gen.go` file in the tree and rewrites them, so never edit
  one by hand or give a hand-written file that suffix: change the definition or the template and run `./build.sh -G`.
- Code for a single operating system lives in the `_darwin.go`, `_linux.go` and `_windows.go` files. Platform-neutral
  code reaches it only through the `api*` wrappers in `platform_api.go`, which also route to the headless backend, and
  a test fails when an `api*` function is declared anywhere else. A new one needs a `native*` implementation for each
  of the three and, unless it concerns the process rather than the screen, a headless one.
- `internal/w32` is excluded from linting, though not from the formatting check. The hygiene tests in its `w32_test.go`
  run on every platform and ban a few patterns outright, such as `syscall.NewLazyDLL` and `runtime.KeepAlive`; the
  comments there say why.
- Tests that start a headless session, usually through the `startHeadless` or `startHeadlessTest` helper, must not
  call `t.Parallel`: a session owns most of the package's mutable globals while it runs. What such a test reads out of
  the application belongs to the UI thread, so read it inside `HeadlessScreen.Do`.
- A test whose outcome depends on the wall clock or on scheduler fairness calls `testenv.SkipTimingSensitive(t)`, which
  skips it on macOS Intel, where the CI runner is too slow for it. Do not loosen its deadlines instead.
- The headless testing example in `README.md` is a verbatim copy of `headless_readme_test.go`, and a test fails when
  the two differ. Edit the test file and copy the result into the README.

## Building, testing and linting

Prefer `./build.sh` over calling `go` directly. It disables cgo, as CI does, and falls back to module mode when the
`go.work` in effect doesn't list this checkout, as happens in a worktree kept inside the tree. `./build.sh -h` lists
every option; the ones that matter day to day are:

- `./build.sh` with no options regenerates the enum sources, builds every package and installs `upack`, the packager
  in `cmd/upack`, with `go install`. `-G` only regenerates. `-g` builds and installs without regenerating.
- `./build.sh -t` runs `go test ./...`. `-r` does the same with `-race`, which needs a C toolchain everywhere but
  macOS, since Go's race runtime requires cgo on the others.
- `./build.sh -f` checks the formatting, printing the diff of anything `golangci-lint fmt` would change.
- `./build.sh -l` runs `golangci-lint run` six times: for darwin, linux and windows, each with and without
  `GOEXPERIMENT=simd`. A single run therefore covers every platform's sources from any machine, though only for that
  machine's architecture. Run only one `golangci-lint` process at a time.
- `./build.sh -a` is the closest local equivalent of CI: generate, build, format check, lint, and tests with `-race`.
  CI also runs `CGO_ENABLED=0 GOEXPERIMENT=simd go test ./...`, so follow it with that, and builds all six OS/arch
  pairs with and without `GOEXPERIMENT=simd`.
- `./build.sh -g -T os/arch` builds for another platform, such as `windows/amd64`. Use it, with and without
  `GOEXPERIMENT=simd` in the environment, when a change touches the `_amd64` or `_arm64` sources, as nothing else
  compiles the ones for the other architecture locally.

Every `-f` or `-l` run asks GitHub for the latest golangci-lint release and installs it into `$(go env GOPATH)/bin`
when the local copy differs, so those runs need network access and may upgrade the tool. Set `GOLANGCI_LINT` to the
path of a binary to use it as is. Running `go test` directly on a single package, such as `go test ./internal/dbus/...`,
is fine for a quick check. Tests built on a headless session need no display. Tests in another operating system's
`_test.go` files are compiled by the lint passes but run only in CI. `go run ./cmd/example` launches a demo that
exercises most of the widgets.
